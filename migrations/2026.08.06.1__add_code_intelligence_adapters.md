# Add Optional Code Intelligence Adapters

Migration ID: `2026.08.06.1__add_code_intelligence_adapters`

## Purpose

Add a provider-neutral code-intelligence layer that supplements GI project
memory with symbol, dependency, change-risk, Git, and code-health evidence
without replacing specifications or creating a hard Repowise dependency.

## Accepted Guidance

- Keep project memory authoritative for requirements, business rules,
  workflows, decisions, runbooks, exact project metadata, and durable notes.
- Use optional code intelligence for symbols, callers/callees, dependency
  graphs, blast radius, Git hotspots, and code-health signals.
- Route mixed intent-and-implementation questions to both layers and preserve
  source labels.
- Keep the provider disabled by default and independently installed/indexed.
- Invoke only allowlisted read-only tools through local MCP stdio.
- Compare provider indexed commit with current Git HEAD and report dirty
  worktrees separately; fall back to current source when unavailable or stale.
- Keep provider indexes ignored and never let status/query operations install a
  provider, rebuild an index, mutate code, or generate editor configuration.

## Project Files To Update

- Add the `code_intelligence` section from the RAG template without overwriting
  project-specific source groups, retrieval settings, or rebuild state.
- Copy `tools/project-memory/code_intelligence.py` and the adapter pattern.
- Merge `.repowise/` into `.gitignore` when Repowise is selected.
- Keep `enabled: false` until the project has reviewed and installed a provider,
  created its index, and verified its allowlisted tools.
- Record a project-specific provider command/version only when selected; do not
  copy private absolute paths or credentials.

## Verification

- Parse updated JSON files.
- Run `python -m unittest tests.test_code_intelligence -v` in the source kit or
  equivalent adapter checks in a consuming project.
- Run `python .\tools\project-memory\code_intelligence.py status` and confirm a
  clean disabled result before provider activation.
- Confirm all configured generated paths are ignored.
- After activation, verify context and risk results against current source and
  inspect freshness metadata.
- Run `git diff --check`.

## Conflict Handling

Preserve stricter project-local privacy, tool allowlist, freshness, and external
path rules. Do not enable or install a provider automatically. If a project has
an existing code-analysis integration, map it to the neutral capability and
freshness contract instead of replacing it blindly.
