# Default Config Service Off For New Projects

Migration ID: `2026.08.02.1__default_config_service_off_for_new_projects`

## Purpose

Make config-service integration opt-in for new GI projects without disabling
existing projects that already use it.

## Accepted Guidance

- Store the project-level integration toggle as `config_service.enabled` in
  `tools/project-memory/instruction-kit.json`.
- Fresh GI bootstraps explicitly set the toggle to `false`.
- Preserve existing behavior during updates: if an existing project's metadata
  has no `config_service.enabled` field, leave it absent and interpret its
  effective value as legacy `true`.
- Use `gi config on/off`, `gi конфиг вкл/выкл`, `gi конфиг он/офф`,
  `ги конфиг вкл/выкл`, or `ги конфиг он/офф` to write the explicit
  project-level toggle.
- Interpret every short `gi config <toggle>` / `ги конфиг <тумблер>` form as the
  whole-project integration toggle. Require an explicit `service`/`сервис`
  segment for the separate app self-registration toggle.
- When the integration is disabled, do not query config-service, self-register,
  or require config-service for ordinary local startup. Use only documented
  project-local runtime config and report a blocker if required values are
  missing.
- Commands that inherently depend on config-service must stop with a concise
  disabled-state blocker and point to `gi config on`.
- Keep `gi config service on/off` as the separate app self-registration toggle;
  neither toggle starts or stops the config-service process.

## Project Files To Update

- Merge the command aliases and toggle semantics into project-local
  `COMMANDS.md` and
  `patterns/AGENTS_RUNTIME/08-config-service-and-task-manager.md`.
- Merge conditional startup and configuration-boundary guidance from the
  corresponding source files; remove unconditional config-service requirements
  when the project toggle is off.
- Do not add `config_service.enabled: false` to an existing
  `tools/project-memory/instruction-kit.json`. Recording this migration as
  applied must preserve an absent field so working integrations stay enabled.
- If a project already has an equivalent explicit config-service integration
  setting, preserve its current value and map the GI command to that documented
  source of truth instead of creating a competing flag.

## Conflict Handling

If a project already documents a different config-service toggle location,
preserve that setting and current effective state. Do not create two independent
toggles. If the current effective state cannot be determined safely, leave it
unchanged and report the ambiguity rather than defaulting the existing project
to off.
