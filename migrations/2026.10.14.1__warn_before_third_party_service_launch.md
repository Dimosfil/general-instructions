# Warn Before Third-Party Service Launch

## Purpose

Ensure the user receives advance notice before an agent starts or restarts a
third-party service, even when the launch is already authorized. Cover local,
remote, containerized, and indirect launches without adding an approval gate.

## Source Files

- `AGENTS.md`
- `templates/AGENTS.template.md`
- `templates/instruction-kit.template.json` (fresh-install baseline)
- `patterns/AGENTS_RUNTIME/09-runtime-and-defaults.md`

## Project Files And Merge Rules

1. Merge the third-party service warning and runtime-module pointer into the
   current project's `AGENTS.md` safety section, using the copied-project
   template. Preserve project-owned instructions and existing approvals.
2. Merge the advance-notice bullets from the runtime module into the project's
   `patterns/AGENTS_RUNTIME/09-runtime-and-defaults.md`; create the module from
   the source if missing. Preserve project-specific run commands and settings.
3. Require notice before the launch command: service name, purpose, local or
   remote location, and applicable effects. Include supporting service
   dependencies and launches caused by scripts, installers, test runners, or
   container commands. Queries to already-running services are not launches.
4. Keep notice separate from permission. Existing authorization does not waive
   notice; notice itself does not require confirmation or replace approvals.
5. Apply idempotently: skip equivalent existing rules and avoid duplicate
   bullets. Report conflicts rather than overwriting project-owned controls.

## Verification

- Review direct, already-authorized, local/containerized, and indirect launches:
  each requires a user-visible notice before execution.
- Verify that querying an already-running service needs no launch notice and
  that existing approval requirements remain intact.
- Verify the entrypoint points to the existing runtime module.
- Run `git diff --check` when Git is available; for shared-library maintenance,
  run the existing bootstrap and context-routing checks.
- Record the migration in instruction-kit metadata only after application and
  verification. Do not start a service merely to verify this text-only rule.

## Conflicts And Rollback

Preserve stricter project-owned controls. If the rule cannot be merged safely,
report the conflicting section and leave the migration unapplied. Roll back
only this migration's owned additions without reverting unrelated changes.
