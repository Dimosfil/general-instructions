# Separate Migration Installation From Host Activation

Version: `2026.10.25.2`

## Applicability

The accepted [installation/host applicability contract](README.md#installation-and-host-applicability)
governs the entire pending batch, including older Verify And Record language.
Codex trust, CLI omission and Desktop service tests are Codex runtime checks;
OpenCode plugin loading and response-loop tests are OpenCode runtime checks.
Unavailable or failed runtime activation does not make verified file changes
unapplied. Never report active/live-tested without evidence.

## Apply

1. Preserve local project rules, customizations, update opt-outs and unrelated
   changes. Merge the applicability rules from `patterns/AGENTS_RUNTIME/07-startup.md`
   and the corresponding loading-contract bullet from `templates/AGENTS.template.md`
   into the local instructions; do not replace the project entrypoint.
2. Refresh `tools/check-instruction-kit-updates.ps1` from the accepted
   `templates/check-instruction-kit-updates.template.ps1`, preserving local changes.
   Keep `tools/get-gi-context.ps1` current so the applicability handoff reaches
   the agent. Merge `BOOTSTRAP.md`, `docs/gi-lifecycle-hooks.md` and
   `docs/gi-opencode-hooks.md` applicability notes and focused project memory.
3. Finish the ordered pending file batch, including the shared lifecycle engine,
   Codex manifest, OpenCode adapter and ignore rules from preceding migrations.
   Do not wait for Codex activation before installing the OpenCode adapter, or
   vice versa. Compare owned installed files with accepted source or verify the
   scoped local merge. Missing files, merge conflicts and failed installation
   checks remain blockers. Do not copy source development tests into products.
4. Revisit earlier pending/skipped IDs caused solely by unavailable host trust,
   reload or live tests. Resolve that installation blocker only after verifying
   their file changes. Do not clear explicit opt-outs or unrelated unresolved
   file blockers. Record the whole completed batch with the local checker's
   `-RecordApplied` only when every pending file migration is verified; the
   current recorder advances the entire batch and must not hide partial work.
5. Recheck installed version and pending count. Report installation separately
   from each host's configured/active/trusted/live-tested state. Keep unavailable
   or failed runtime checks explicit with reason and next action; use manual
   Work/Complete until hooks are verified. Any explicitly requested runtime
   activation/live verification remains unfinished until it passes.

## Verify

- In a consuming project, verify installed files/merges and metadata recording;
  no other host's UI, credentials, trust or external model is required for this.
- In source maintenance, run context-routing/update and bootstrap regressions.
  Cover historical skipped IDs plus later adapters, read-only checks before
  recording, zero pending after recording, retained opt-outs and separate
  unverified runtime evidence. Keep context budgets and lifecycle enforcement.
